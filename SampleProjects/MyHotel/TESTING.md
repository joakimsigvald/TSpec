# MyHotel — testing

**Purpose:** MyHotel's automated testing: which suite states what, how a spec is written, and how
each suite is run.

## Which suite states what

A claim is specified at the layer that owns it:

- `Host.Spec`, subject `Hotel` over HTTP with its own data files, states what Core.Spec's mocks
  stand in for, each once: every route on its success path, every exception Contract declares as
  its status and code, every store by what a restart reads back and a new hotel starts with, and the
  wiring and configuration behind each interface Core mocks. A spec that only a bug in Core could
  fail belongs in Core.Spec.
- `Core.Spec`, a Core class with its collaborators mocked, states the domain rules: what is unique,
  kept in order, refused. A folder per class, a `When…` class per method.
- `Web`, by its Vitest tests, states what the user sees and what each action sends.

Contract and Entry get no specs: Entry's mapping is stated end to end. Never restate a status code
in Core, or a domain rule over HTTP.

## Writing a spec

- A spec claims only what its `When` returns: an operation that reports a bare `bool` states the
  flag, and its effect under the read that observes it. Design Core's interfaces with that in mind.
- A refusal also states something only its handler could produce, such as the room number in the
  error body: a 404 alone holds just as well when the route does not exist.
- Each value shows what the precondition needs of it, never an arbitrary pick: a mention when any
  value will do, a tag when any will do but the claim names its role (`Tag<int> bedCount`), one
  derived from another when the claim rests on how they relate (`The<int>() + 1`), and the domain's
  name for it when it has one, kept in a spec project for every spec to share, as Core.Spec's `Time`
  holds `Today` and `Tomorrow` for both suites. A literal only when the value itself is the claim.
- Write out only what the claim rests on and what keeps the rest of the input valid. Leave the rest
  to generation, with `A<T>() with { … }` or `Using(value)`, rather than spelling it out as
  mentions, and of the forms that do this, choose the one that reads best. `new T(…)` is the last
  resort: only when no other form reads better, or it is the shortest of those that read as well.
- Do not pin rendering with `Specification.Is`: `Core.Test` already locks it, and a rendering change
  shows in the committed `_specification` diff.
- TSpec usage: the repository's [agent-reference.md](../../agent-reference.md), and
  [Architecture.CSharp/agent-reference.md](../../Architecture.CSharp/agent-reference.md) for the
  rules on the code. Both are working copies, so they may run ahead of the packages MyHotel
  references.

## Running the specs

Run a spec project with `dotnet test SampleProjects/MyHotel/Host.Spec` (or `Core.Spec`,
`Architecture.Spec`), narrowed with `--filter-class`. The `_specification` files are regenerated by
a green run: never edit them, and read their diff when reviewing a change.

## Vitest

- Vitest and Testing Library, one test file per view, beside it (`Rooms.test.tsx`). The API is faked
  by `src/test/fakeApi.ts`: each test declares the replies it needs, and an undeclared request fails
  it.
- A test does what the user does - type, click - and asserts what the user sees, by role, accessible
  name and description; never component internals, state or class names.
- A test of an action also asserts what was sent: the method, the path and the body the API
  received.
- A refusal is asserted as the Swedish text in the place the user finds it
  (`toHaveAccessibleDescription`), stating both the wording and the link to its field or button.

`dotnet test` does not run them:

```bash
npm --prefix SampleProjects/MyHotel/Web test
```

Web is green only when its lint is too:

```bash
npm --prefix SampleProjects/MyHotel/Web run lint
```
